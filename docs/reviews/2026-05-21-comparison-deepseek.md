## 一、Minimax 报告逐条合理性分析

### 1.1 合理的发现 ✅

| # | 发现 | 判断 | 说明 |
|:---|:---|:---:|:---|
| 1.2.1 | transactions 无 `session_id` 导致收入归因模糊 | ✅ | 真实的数据模型限制。非代码bug，但是有价值的工程观察——同一客户多会话多渠道时，收入无法精确归属到具体会话的流量来源 |

| 3.2.2 | 年度损失三年均值但数据质量不一致 | ✅ | 2021-2023 会话量差异巨大（421K→155K→56K），用三年综合数据推算单年损失会产生误导 |

| 3.2.4 | 热力图样本量门槛应增加 Wilson CI | ✅ | 仅用 ≥1000 会话的绝对门槛，对小样本（如 tablet 仅 7,601 会话）波动敏感 |

### 1.2 不合理或过度要求的发现 ❌/⚠️

| # | 发现 | 判断 | 详细分析 |
|:---|:---|:---:|:---|
| **4.2.1** | **瀑布图累积线"连接柱顶而非柱底"** | ❌ **硬伤** | 这是 Minimax 报告最明确的错误。以下逐行验证 |

#### 瀑布图代码验证（Minimax 4.2.1 是错误的）

[visualization.py:307-322](../../python/visualization.py#L307-L322) 的实际逻辑：

```python
# n=4, values=[v0, v1, v2, v3]
cumulative = np.zeros(n + 1)     # [0, 0, 0, 0, 0]
bottoms = np.zeros(n)            # [0, 0, 0, 0]

for i in range(n):
    bottoms[i] = cumulative[i]   # bottoms = [0, v0, v0+v1, v0+v1+v2]
    cumulative[i+1] = cumulative[i] + values[i]
# cumulative = [0, v0, v0+v1, v0+v1+v2, v0+v1+v2+v3]

# 柱体：bar[i] 从 bottoms[i] 到 bottoms[i]+values[i]
# bar0: [0,        v0          ]  → 线点 (0, 0)         = bar0 底部（累积起点）
# bar1: [v0,       v0+v1       ]  → 线点 (1, v0)        = bar1 底部 = bar0 顶部 ✓
# bar2: [v0+v1,    v0+v1+v2    ]  → 线点 (2, v0+v1)     = bar2 底部 = bar1 顶部 ✓
# bar3: [v0+v1+v2, v0+v1+v2+v3 ]  → 线点 (3, v0+v1+v2)  = bar3 底部 = bar2 顶部 ✓

ax.plot(range(n), cumulative[:-1], 'D-', ...)
# cumulative[:-1] = [0, v0, v0+v1, v0+v1+v2] ← 正确！
```

这**正是标准瀑布图累积线的正确做法**：线从原点出发，依次经过每根柱子的底部（=上一根柱子的顶部），形成阶梯式累积视觉。

Minimax 建议改为 `cumulative[:-1] - values = [-v0, v0-v1, v0+v1-v2, ...]` 会产生负值，完全错误。

| # | 发现 | 判断 | 详细分析 |
|:---|:---|:---:|:---|
| 2.2.1 | Welch's t 检验应增加 Shapiro-Wilk 正态性验证 | ⚠️ **过度要求** | 流失组和转化组各有数万样本，中心极限定理已提供充分的稳健性保证。在大样本下 Shapiro-Wilk 对微小偏离也显著（p<0.001），反而产生误导性警报。增加正态性检验在此场景下属于**过度工程化** |
| 2.2.3 | Cramér's V 函数参数 `min_dim` 应改为 `min_cat` | ⚠️ **吹毛求疵** | 命名偏好问题。`min_dim` 在统计学文献中也常见（"smaller dimension of the contingency table"），不影响功能或可读性 |
| 4.2.2 | 热力图文字对比度"过于简单" | ⚠️ **吹毛求疵** | 当前 `mid_val` 阈值判断在实际使用中效果可接受。属于可优化项，不是问题 |
| 6.2.3 | 中文文件名跨平台问题 | ⚠️ **过度谨慎** | 现代文件系统（Linux ext4、macOS APFS、Windows NTFS）完全支持 Unicode 文件名。排序问题可通过日期前缀规范解决（当前已使用 `260520_` 前缀），不需要强制改为英文 |
| 5.2.2 | 渠道 KeyError 风险 | ⚠️ **夸大风险** | 代码已有 `if ch in base.index and ch in curr.index` 保护，不会发生 KeyError。Minimax 自己也承认了这一点。建议增加日志警告是合理的，但不应列为"问题" |

## 四、综合评判

### 4.1 哪个报告更合理？

**DeepSeek 报告更全面、更贴合业务实际；Minimax 报告在部分代码细节上更细致，但有一处硬伤。**

| 评判维度 | 更优报告 | 原因 |
|:---|:---:|:---|
| **概念性/方法论深度** | DeepSeek | 识别出损失量化公式的根本性概念缺陷——这是影响最大的发现，直接关系到核心业务结论的可信度 |
| **覆盖面广度** | DeepSeek | 多了 Power BI、业务策略成本、测试数据质量、可复现性、无障碍设计等多个视角。Minimax 完全未覆盖 Power BI 层 |
| **代码细节精度** | **Minimax** | 抓住了 Cohen's d ddof、PIE Importance 分母、Cohort size=0、原位修改一致性等 DeepSeek 漏掉的细节 |
| **可视化判断准确性** | DeepSeek | Minimax 的瀑布图判断（4.2.1）是明确的硬伤——代码验证表明瀑布图累积线画法是正确的 |
| **统计严谨性** | 持平 | 各有侧重。DeepSeek 指出多重比较不完整和 SQL 事件级混淆；Minimax 指出 ddof 细节但过度要求正态性检验 |
| **业务相关性** | DeepSeek | 损失金额区间估计、策略 ROI 计算、速赢矩阵、行业对标——这些直接关乎业务方如何使用分析结果做决策 |
| **修复方案可操作性** | DeepSeek | 每个问题都给出了完整的代码修复方案 + 工时估算 + 三阶段时间线 |

### 4.2 两篇报告的关系

两篇报告是**互补**而非竞争关系：

- **DeepSeek 报告做主干**：覆盖面广（9个角度）、业务相关性强、概念性分析深入、修复路线图完整
- **Minimax 报告的 5 个细节发现做补充**：弥补了 DeepSeek 在代码级精度上的少数遗漏

两份报告加在一起形成了目前该项目**最完整的审查体系**。

### 4.3 Minimax 报告不应采纳的点

| 发现 | 原因 |
|:---|:---|
| 瀑布图累积线修改（4.2.1） | **代码验证表明当前实现是正确的**。建议的修改方案会产生负值 |
| 强制增加正态性检验（2.2.1） | 大样本下过度工程化，Shapiro-Wilk 会产生误导性显著结果 |
| 中文文件名必须改为英文（6.2.3） | 现代文件系统完全支持 Unicode，当前日期前缀命名规范已解决排序问题 |

## 五、建议采纳清单

### 5.1 两份报告共有的发现（约 12 个）

以下发现两份报告一致，可信度最高，应优先处理：

- PIE Ease 主观赋值需要透明化说明
- 年度损失估算需要标注数据完整性前提
- Shift-Share 需要完善渠道一致性和数据完整性验证
- 品类漏斗/热力图需要增加 Wilson 置信区间
- 流失特征存在因果困境（tautology）需在文档中标注
- 部分工具函数缺少文档字符串
- AOV=0 等边界情况测试覆盖不足

### 5.2 仅 DeepSeek 报告中的发现（约 16 个）

全部合理，建议全部采纳。按优先级排序：
1. **P0-1** 损失量化公式修正（影响最大）
2. **P0-4** main.py 去重导入
3. **P0-8** SQL 统计检验改为会话级
4. **P0-12** CRO 策略增加成本估算
5. **P0-13** 损失金额增加 Bootstrap CI
6. **P0-24** README 增加运行前检查清单
7. 其余 P1/P2 项按路线图推进

### 5.3 仅 Minimax 报告、建议额外采纳的发现（5 个）

| # | 发现 | 优先级 | 采纳建议 |
|:---|:---|:---:|:---|
| 2.2.2 | Cohen's d 函数 `a.std()` → `a.std(ddof=1)` | P1 | **采纳**。虽然大样本下影响极小，但代码规范上应保持一致 |
| 5.2.3 | PIE Importance 分母改为 `len(funnel_wide)` 或 rank-based | P1 | **采纳**。统一分母后各阶段 I 值具有可比性 |
| 第7节 | Cohort `.get(idx, 1)` → `.get(idx, 0)` 并处理 else 分支 | P0 | **采纳**。边缘情况可能导致留存率完全错误 |
